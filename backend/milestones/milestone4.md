# Milestone 4 — Receipts, Expenses, Bank Accounts, Transfer, Payroll

**Goal:** The remaining sidebar TRANSACTIONS entries: Receipts, Expenses, the cheque lifecycle
both can produce, Bank Accounts (setup, but a hard dependency of cheque deposit / Online payment
mode so it lives here), Transfer (Cash ↔ Bank), Wage Run (piece-rate), and Salary Run (monthly).
Ledger-only postings throughout (no stock movements) — Wage Run is the one exception that reads
`dbo.articles`' 12 stage-cost columns but still only writes `ledger_entries`.

**2026-08-19 update:** this milestone was expanded from its original Receipts/Expenses-only scope.
Bank Accounts, Transfer, and Payroll (Employees/Wage Run/Salary Run) all had complete tables
already sitting in `database/schema.sql` — `bank_accounts`, `cheques`, `transfers`, `employees`,
`stages`, `worker_stages`, `wage_runs`/`wage_run_items`, `salary_runs`/`salary_run_items` — plus
two fully-written design docs, `System_architecture/cash_and_bank.md` and
`System_architecture/payroll.md`, that were never folded into any milestone. **Read those two docs
before starting the relevant module below** — they cover screens, posting rules, edit/unpost
behavior, and open decisions in far more depth than these checklists restate.
`database_schema_v4.3.md`/`use_cases.md` do NOT describe these tables (that's why Module 7.1 used
to say "blocked, no definition exists") — `payroll.md`/`cash_and_bank.md` are the actual source of
truth for this scope, not those two files.

**Posting rules:** Post receipt: debit CASH / credit customer. Post expense: debit expense head
(business account) / credit CASH. Post transfer: debit `to_ba_id` / credit `from_ba_id`
(`cash_and_bank.md` §7). Post wage run: debit WAGES EXPENSE / credit worker BA. Post salary run:
debit SALARIES EXPENSE / credit each salaried employee's BA, one credit line per employee
(`payroll.md` §6). **Reverse-never-erase:** bounced cheques/receipts get a reversing entry, not a
deleted row (schema §6.1); wage/salary run unpost is audited (`unposted_at`/`unposted_by`/
`amount_before` columns on both run tables), not a silent status flip.

## Module 4.1 — Receipts / Jamma & Cheque Disposal (UC-25, UC-27)
- [x] `receipts` (ipc handler/service/repository) CRUD + post/unpost (ledger only) — always created `DRAFT` explicitly (same discipline as transfers/wage_runs/salary_runs). Post writes `Dr <cash/bank/cheques-in-hand> / Cr customer BA`: CASH → `CASH_IN_HAND` chart account, ONLINE → the **specific bank's own linked `ba_id`** (not the generic `BANK_ACCOUNTS` chart code — Module 4.3 gives each bank its own account precisely for this), CHEQUE → `CHEQUES_IN_HAND` chart account. Commission > 0 writes a second, wholly separate `Dr COMMISSION_ALLOWED / Cr customer BA` pair — the sale bill itself is never touched (`database_schema_v4.3.md` §7)
- [x] `draftReceipts` — dummy/unconfirmed receipts, CASH/ONLINE only (`dbo.draft_receipts` has a `cheque_id` FK for shape-symmetry but no `cheque_no`/`cheque_date` columns of its own — a genuinely useful draft CHEQUE receipt isn't representable, so it's rejected with a clear message pointing at `receipts:create` instead). `confirm()` = create the real receipt + post it immediately, two sequential transactions (not one shared transaction like `draftPurchases.confirm()` — a receipt has no line items to keep atomic alongside posting)
- [x] `bankAccounts`/`cheques` (ipc handler/service/repository) — a CHEQUE receipt auto-creates a linked `cheques` row (`PENDING`) in the same transaction as the receipt insert. Once the receipt is posted, the cheque can be **deposited** (no ledger entry — the customer was already credited at receipt-post time; deposit only relocates it to a specific bank for balance-tracking, per `cash_and_bank.md` §10's derived-balance formula; "one cheque is never split across two banks" enforced), **endorsed to a vendor** or **used for an expense** (both DO write a ledger entry — Dr target BA / Cr `CHEQUES_IN_HAND`, since this actually moves money to someone else), and can be **split** across multiple partial actions (`recomputeStatus()` derives `DEPOSITED`/`ENDORSED`/`PARTIALLY_ENDORSED` from the remaining un-allocated balance after each action). A fully-deposited cheque can be `markCleared()` — pure status flip, no ledger effect
- [x] **Added a "returned to sender" disposition** (user-requested, beyond the original checklist) — distinct from `BOUNCED`: new `RETURNED` cheque status with its own `returned_date`/`return_reason` columns (migration `002_cheques_returned_status.sql`), same reverse-never-delete mechanics as a bounce, for a non-bank reason (e.g. a due-date issue)
- [x] `bounced_date`/`returned_date` drive the reversal; bounce/return-to-sender writes reversing ledger entries, never deletes the original (reverse-never-erase, schema §6.1) — shared `reverseCheque()` handles both. Reverses every ACTIVE `cheque_allocations` row for the receipt (flips to `REVERSED`, writes an opposite ledger pair — **except for `DEPOSIT` allocations, which never had a ledger entry to reverse in the first place**; caught as a real bug mid-session when the first live test run hit `CK_ledger_entries_one` trying to reverse a deposit with no account on either side, fixed and re-verified), then reverses the receipt's own ledger effect (only if it was `CONFIRMED`) using the exact same account-resolution logic posting used, so the reversal always lands back on the same account
- [x] **Found and fixed a real schema bug**: `CK_receipts_cheque` as originally written is literally impossible to satisfy given the schema's own documented two-step insert plan (SQL Server checks `CHECK` constraints per-statement, not deferred to commit) — relaxed via migration `003_receipts_cheque_check_relax.sql`; the "every CHEQUE receipt eventually gets a real `cheque_id`" guarantee now lives at the application layer instead
- [x] Weekly/Monthly/Overall list filters — same `resolveDateRange()` convention as every other module
- [x] Verify: record a cheque receipt → mark bounced → confirm a reversing ledger entry exists and the original row is untouched — verified live and far beyond this single scenario (see `PROGRESS.md` for the full list: partial deposit, cross-bank rejection, split endorsement, full deposit + clear, double-post/double-bounce/double-clear all rejected, unpost blocked once a cheque is disposed of, return-to-sender, draft CRUD + confirm, update/remove guards) — debugger review clean after fixing 2 issues: `draftReceipts.confirm()`
  refactored into one atomic transaction (was 2 separate ones, a duplicate-receipt risk on
  retry-after-failure — re-verified live with a forced mid-transaction failure), and a missing
  chart-account null-check added to `cheques.service.js#reverseCheque()`'s commission-reversal
  branch for consistency with every other lookup in the module

## Module 4.2 — Expenses / Kharch (UC-26)
- [x] `expenses` (ipc handler/service/repository) CRUD + post/unpost (ledger only), expense head = business account (vendor or any other business account — `resolveTarget()` accepts either `vendor_id` or `ba_id`). Four payment modes: CASH (`Dr ba_id / Cr CASH_IN_HAND`), ONLINE (`Dr ba_id / Cr` the specific bank's own `ba_id`), CHEQUE_ISSUED (`Dr ba_id / Cr` the specific bank's `ba_id` — bank debited the day the cheque is *written*, deduct-on-write, `cash_and_bank.md` §6; `issued_cheque_no`/`issued_cheque_date` are plain columns, no separate `cheques` row since that table is for cheques *received*), and CHEQUE_ENDORSED
- [x] **CHEQUE_ENDORSED deliberately writes no ledger entry of its own** — `post()` delegates entirely to `cheques.service.js#endorseToExpense()` (the exact same function the standalone Cheques page uses, already debugged clean), so there is only ever ONE ledger trail per cheque disposal regardless of which screen triggered it, and the existing bounce/return-to-sender reversal handles it correctly with zero new reversal code. `unpost()` is deliberately BLOCKED for this mode (`USE_CHEQUE_REVERSAL`) — the only correct undo path is the cheque's own reversal mechanisms, not a generic unpost
- [x] `draftExpenses` — dummy/unconfirmed expenses, all FOUR payment modes representable (unlike `draftReceipts`, which can't draft a CHEQUE receipt — a `CHEQUE_ENDORSED` draft references an *already-existing* received cheque, no chicken-egg problem)
- [x] Weekly/Monthly/Overall list filters — `resolveDateRange()` added to both `expenses.service.js` and (correction) `receipts.service.js`, which despite an earlier progress-log claim never actually had it either — caught while building this and fixed for both
- [x] Note: payment-overdue alert is dropped in v4.3 — only cheque-due alerts remain (Milestone 9) — unaffected by this module
- [x] **User-requested addition beyond this checklist: "Cheque Return"** — undo ONE specific endorsement (e.g. a vendor hands the cheque back) without touching the cheque's other allocations or the underlying receipt at all — narrower than `bounce()`/`returnToSender()`, which reverse every active allocation on a receipt. New `cheques.service.js#reverseAllocation()`, `listEndorsedAllocations()`, and matching `cheques:reverse-allocation`/`cheques:endorsed-allocations` IPC channels
- [x] **Found and fixed 5 real bugs this pass, across 3 debugger review rounds** (see `PROGRESS.md` for full detail): (1) `expenses.payment_mode`/`draft_expenses.payment_mode` were `VARCHAR(10)`, too narrow for `CHEQUE_ENDORSED`/`CHEQUE_ISSUED` — widened via migration, AND the app code's own `sql.VarChar(10)` parameter declarations (a separate thing from the DB column) had to be fixed too, since Tedious enforces the declared width regardless of the actual column; (2) `draft_expenses` had drifted out of parity with `expenses` (stale `'CHEQUE'` mode, missing `issued_cheque_no`/`date` columns) — brought back in sync via migration; (3) **HIGH** — `post()` on a `CHEQUE_ENDORSED` expense wasn't atomic across its two separately-committing steps, risking a double-disposal on retry — fixed by adding a `cheque_allocations.expense_id` back-reference so `post()` can detect and skip a redundant re-disposal; (4) LOW — added a DB-level `UNIQUE INDEX` on `cheques.receipt_id`, previously only an app-level invariant; (5) **MEDIUM-HIGH, found verifying fix (3)** — `draftExpenses.confirm()` still minted a brand-new expense on every retry (the realistic recovery path, via the Drafts UI), so post()'s per-expense_id idempotency check never found the prior attempt — fixed with a `draft_expenses.pending_expense_id` back-reference so any confirm() retry resumes against the SAME expense_id, plus a guard blocking `remove()` on a draft with an unresolved pending expense (would otherwise orphan it)
- [x] Verify: CASH/ONLINE/CHEQUE_ISSUED all posted with correct ledger pairs; CHEQUE_ENDORSED against a real posted cheque correctly resulted in zero expense-sourced ledger rows and the correct CHEQUE_ALLOCATION-sourced pair; unpost blocked for CHEQUE_ENDORSED; `reverseAllocation()` correctly freed the cheque's balance and left the linked expense's status untouched; draft CRUD + confirm (all 4 modes); the compensating-delete safety net verified with a genuine no-allocation failure; the fix-3 idempotency verified by directly simulating the exact failure window (endorseToExpense() succeeds, status-flip skipped) then retrying post() — no duplicate allocation; the fix-5 resume verified by simulating a stuck confirm() (pending_expense_id set, real allocation created, status never flipped) then calling confirm() again on the same draft — correctly resumed against the same expense_id, no duplicate expense or allocation, draft only deleted on the successful resume — all run live against `wentox_db`. Third debugger review round: clean (confirmed round-2's fix genuinely closes the gap for every throw point in `post()`, not just the one tested), plus one LOW finding — deleting a stuck expense directly (bypassing the Drafts UI) would hit the new FK constraint with an opaque error — fixed with a matching `PENDING_DRAFT_UNRESOLVED` guard on `expenses.service.js#remove()`, re-verified live
- [ ] Frontend: no Expenses/Cheque-Return page connected to real data — new `ChequeReturnPage.tsx` built (per explicit "build but don't connect" instruction), not wired into navigation or the demo reducer

`ledger_entries` — no stock movement. `rate`/`packing` are **snapshotted** onto each
`wage_run_items` row at posting time, deliberately diverging from `dbo.articles` later so editing
