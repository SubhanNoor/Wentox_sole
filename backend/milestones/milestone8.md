# Milestone 8 — System Setup: City Creation & Accounts Hierarchy

**Goal:** The remaining sidebar SYSTEM SETUP entry (City Creation) plus its supporting location
setup, and the 3-level accounting hierarchy (Class → Group → Chart/Business) every earlier
transaction milestone posts against. **v4.3 dropped `control_accounts` entirely** — the hierarchy
is Group → Chart or Group → Business directly, one level shallower than previously planned.

## Module 8.3 — Chart & Business Accounts, Hierarchy Queries (UC-16, UC-17)
- [x] `chartAccounts` (ipc handler/service/repository) CRUD — auto-code `<group.code><2-digit serial>` (§3.2; matches the majority of already-seeded reserved codes, e.g. group `1000`+`01`→`100001` CUSTOMERS ACCOUNTS — 4 payroll codes `220001/220002/410001/410002` are pre-existing outliers under no real group row, flagged not fixed, a Module 4.5 historical artifact). `group_id` fixed at creation. No hard delete at all — UC-16's "reserved accounts must not be deleted" is satisfied by there being no delete endpoint; "remove" = `status → CLOSED` (this table's only soft-delete mechanism, no `is_active` column), blocked outright for any reserved code (`RESERVED_ACCOUNT`). `is_restricted` rows (Cash at Banks, Directors Drawings) hidden from non-ADMIN sessions in `list()`/`get()`, same `session.role === 'ADMIN'` check `reports.service.js#paymentTrail()` already uses (TASK-14)
- [x] `businessAccounts` (ipc handler/service/repository) — filled in `list()`/`update()`/`remove()`/`reactivate()` alongside the existing `createUnderChartCode()`/`getById()`/`getCashAccount()`. Same CLOSED-exclusion and restricted-parent-hiding as chartAccounts. `remove()` blocked outright (`PARTY_LINKED_ACCOUNT`) for any account already owned by a vendor/customer/employee/bank — those manage their own account from their own setup screen, not this one. No duplicate-name check (UC-17 doesn't call for one; no DB-level `UNIQUE(name)` either)
- [x] `accounts:tree` — new `accountsTree.repository.js`/`.service.js`/`accounts.ipc.js` (a read-only cross-entity view, not CRUD for one table, hence its own small feature rather than living inside chartAccounts/groupAccounts). One joined query, Class→Group→Chart→Business nested in the service; `is_restricted` chart accounts (and everything under them) dropped entirely for non-ADMIN, same as chartAccounts/businessAccounts' own list()
- [x] Auto-fill lookup: `chartAccounts:get`/`chart-accounts:get` returns the full joined row (its own `group_id`/`group_name`/`class_id`/`class_name`) — enough for a future Sale Bill/Receipt auto-fill screen to consume without a second round-trip; no such screen built (out of scope — those modules are already complete without it)
- **Bug caught while cross-checking against existing convention, before a debugger pass even ran:** every new multi-word-feature `.ipc.js` file (`businessAccounts`, `chartAccounts`, `groupAccounts`, `accountClasses`) was registering camelCase channel prefixes (`businessAccounts:list`), but `preload.js`'s `camelToKebab()` only ever computes a kebab-case prefix (`business-accounts`) from the `FEATURES` array — every one of those channels would have been unreachable from the renderer. Fixed across all four files (including the `businessAccounts:getCashAccount` channel added in the earlier Cash/Transfer fix this same day) to match `bankAccounts.ipc.js`/`subCustomers.ipc.js`'s existing kebab-case-prefix convention. `accounts:tree`/`expenses:*` were unaffected (single-word features, no case conversion happens either way)

Needs `npm run seed`/`npm run migrate` (no schema change here — `account_classes`/`group_accounts`/`chart_of_accounts`/`business_accounts` already exist) + live CRUD through each new channel, on a machine with `wentox_db` running.
