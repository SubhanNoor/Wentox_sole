## Live backup database — follow-up (new scope, not in the original milestone list)
- **What was asked:** a second, live SQL Server database mirroring the main one, kept in sync automatically but never blocking main writes if it's briefly out of sync, plus a manual "Backup Now" button; the install-time NSIS wizard fixes the main install path (unchangeable) but adds one page asking where this backup database's files should live.
- [x] **Sync mechanism — native `BACKUP DATABASE`/`RESTORE DATABASE`, not row-by-row dual writes.** Replaying the same insert independently against two databases risks `IDENTITY` columns drifting apart (e.g. a sale bill header id vs. its item rows) — silently corrupting the "mirror" over time. `BACKUP DATABASE [main] TO DISK` then `RESTORE DATABASE [backup] FROM DISK WITH REPLACE` instead copies the exact committed state, ids included, every time, so it can never drift. `backend/src/services/backup.service.js`.
- [x] `ensureBackupDatabase()` — lazily creates the backup DB (`CREATE DATABASE ... ON (FILENAME=...)`) the first time a sync runs, using the folder from `appConfig.getBackupDbFolder()`, not at every startup.
- [x] `sync()`/`syncIfDirty()` — a module-level in-flight promise means a manual "Backup Now" click during an auto-sync just awaits the same run rather than racing a second `RESTORE`. `pool.js#withTransaction()` sets a `dirtySinceLastBackup` flag on every commit (every real write in this codebase goes through `withTransaction`, per the existing "Posting" convention); the 10-minute timer in `electron/main.js` calls `syncIfDirty()`, which no-ops (skips the BACKUP/RESTORE entirely) when nothing was written since the last sync. Failures are caught and logged, never surfaced to/blocking a main-DB write.
- [x] `backup:runNow`/`backup:status` IPC channels (admin-only, `requireRole('ADMIN')`) — `src/ipc/backup.ipc.js`; `frontend/src/pages/SettingsPage.tsx` gained a "Backup Database" card (admin credentials tab) with a Backup Now button and last-sync-time display.
- [x] **Install-time config:** `build/installer.nsh` — one custom NSIS page (via the `customPageAfterChangeDir` hook) asks for the backup folder, writes `%APPDATA%\Wentox\backup-config.json` (`{"backupDbFolder": "..."}`, backslashes converted to forward slashes since Node's `fs`/`path` accept either on Windows and it sidesteps JSON-escaping). `src/config/appConfig.js` reads/writes that file via Electron's `app.getPath('userData')` at runtime — `app.setName('Wentox')` added to `main.js` so that resolves to the same `%APPDATA%\Wentox` the installer wrote to (package.json's `name` is the npm-package `wentox-backend`, not this).

- [x] **Real root cause of the `warning 6010` build failures (three CI cycles): electron-builder compiles `installer.nsi` TWICE.** The first pass defines `BUILD_UNINSTALLER` to emit the uninstaller executable. - [x] **Final consolidated database setup — root cause of the auto-install failure found.** `SQLEXPR_x64_ENU.exe` is a **self-extracting archive, not setup itself**: setup parameters cannot be passed to it directly, which is precisely what exit code `0x84C4000B` (-2067529717) was. The documented sequence is `/x:<dir>` to extract first, *then* run the extracted `setup.exe` with the real parameters ([silentinstallhq](https://silentinstallhq.com/microsoft-sql-server-2022-express-silent-install-how-to-guide/), [Advanced Installer](https://www.advancedinstaller.com/forums/viewtopic.php?t=36298)). That final verification step matters: every previous iteration assumed success and reported an exit code with no idea whether the app could actually connect. Two robustness fixes found while writing it: `3010` (success, reboot required) is treated as success rather than failure, and the sysadmin group is resolved from its well-known SID `S-1-5-32-544` rather than hardcoding the English `BUILTIN\Administrators`, which setup rejects on a localised Windows.
- [x] **Installer now asks for exactly one thing: a password** (plus the backup folder). A remote/non-standard server is still reachable by editing `%APPDATA%\Wentox\app-config.json` afterwards. Password confirmation field added, and a double-quote is rejected on the page (and again in the script) since setup's command line has no way to escape one.

- [x] **`app-config.json` is now written by `setup-sqlserver.ps1`, not NSIS — the cause of the final `ELOGIN`.** Setup exited 0, meaning its own verification step genuinely connected as `sa` over `localhost,1433`; the app nonetheless failed to log in, which can only mean the config held a *different* password than the one actually set on `sa`. The culprit was the hand-rolled `JsonEscape` macro in NSIS (two chained `${WordReplace}` calls with a `"+"` option) mangling the value on its way into the file. Rather than repair that escaping, the whole responsibility moved to the PowerShell script, which already holds the exact password it is about to verify and can emit correct JSON via `ConvertTo-Json`. Written up-front, *before* any install work, so a failed SQL Server install still leaves the app with a valid config — fix SQL Server by hand later and Wentox just works, with no second file to repair. Emitted as UTF-8 **without** a BOM, since `JSON.parse` chokes on a leading BOM. `JsonEscape` and the NSIS config write are deleted outright.
- **Verified by execution, not inspection**: a password containing a backslash, an apostrophe and a `$`, together with a backslash-laden Windows path, were run through the real `ConvertTo-Json` code path under a locally-extracted `pwsh` and parsed back with Node — both round-trip byte-identical. This is the first part of the install chain that has actually been *run* rather than only compiled.
- [x] **Config moved to `%ProgramData%\Wentox` — the actual reason for the final `ELOGIN`.** The file wasn't corrupt; it wasn't where the app looked. Wentox installs `perMachine`, and electron-builder's NSIS sets the all-users shell context for that, so `$APPDATA` inside `customInstall` resolves to `C:\ProgramData` rather than the roaming profile — while `appConfig.js` read Electron's per-user `userData` (`%APPDATA%\Wentox`). The app therefore found *no* config at all and silently fell back to `.env` defaults (`sa` with an empty password), which is precisely "Login failed for user 'sa'". The same mismatch would bite regardless of the shell context anyway: the installer runs **elevated**, so any per-user path lands in the elevating admin's profile, invisible to whoever actually runs the app. Machine-wide is also simply correct here — one PC, one local SQL Server, one connection, shared by every Windows user on the shop PC. `appConfig.js` now resolves `%ProgramData%\Wentox\app-config.json` (falling back to the old `userData` path so existing installs don't lose settings on upgrade), the script defaults `-ConfigPath` to `$env:ProgramData`, and NSIS no longer passes a path at all rather than propagate its ambiguous `$APPDATA`.
- **Lesson from this whole sequence:** four separate failures (`ESOCKET`, `ELOGIN`, `0x84C4000B`, `ELOGIN` again) each looked like the previous one recurring. Progress only came from making each layer *report* rather than assume — the script's own log, then its end-to-end connection check, then finally noticing setup exited 0 while the app still failed, which localised the fault to the config rather than the database.
- [x] **Fresh installs could never migrate at all — found by running a real SQL Server locally (Docker) instead of guessing.** `database/schema.sql` is a consolidated snapshot that already contains most later migrations' effects (001 `bank_accounts`, 005's widened `payment_mode`, 007, 010, 011) but not all of them (008/009's `vw_overall_directory`), so migrations can't simply be skipped on a fresh database — they have to be individually idempotent.
