## Module 9.1 — Alerts (UC-05)
- [x] `alerts` (ipc handler/service/repository) — `list()`/`dismiss()`. Covers BOTH cheque-due (`cheques.cheque_status IN ('PENDING','PARTIALLY_ENDORSED')`, same filter as `IX_cheques_due`) and sale-bill due-date (`sale_bills.due_date`, re-added post-v4.3 — see `database/schema.sql`'s own comment, which flagged this exact alert as "not wired up yet"). User explicitly asked for both, overriding this checklist's original "payment-overdue alert dropped in v4.3" note — no schema change was needed since `due_date`/`alert_dismissals` were already restored/present in the applied `database/schema.sql`, just unused
- [x] Both kinds are unconditional (no "balance still positive" check) — UC-05's original wording needs a per-bill payment link this schema doesn't have (receipts are customer-level, never tied to one specific bill); matches what was actually asked for (a due-date reminder, dismissible), not UC-05's stale phrasing. 7-day window (`due-soon` amber / `overdue` red once passed), sorted nearest-first per UC-01. `alerts:dismiss` writes a permanent dismissal (`alert_dismissals.dismissed_until` stays `NULL`, matching this table's own "no snooze in this build" comment), idempotent on an already-dismissed key
- **Not live-verified this session** — no SQL Server reachable in this sandbox.
- [x] **Follow-up: alerts now persisted, computed by a startup job, not live on every `alerts:list` call.** New `dbo.generated_alerts` table (migration `011_generated_alerts.sql`, also folded directly into `database/schema.sql`). `alerts.service.js#refreshAlerts()` — the job body — runs the same cheque-due/sale-bill-due queries `list()` used to run live, upserts each into `generated_alerts` by `alert_key`, then deletes any stored row no longer in the fresh set (a cheque cleared/bounced since last run, or a bill's due date aged out of the 7-day window). Called once from `electron/main.js#app.whenReady()`, right after `registerIpcHandlers()` — **not** on a repeating timer (explicit instruction: startup only, no re-run while the app stays open). `alerts.service.js#list()` now just reads `generated_alerts` (cheap, no recomputation) and derives `severity` live from `alert_date` vs today at read time — deliberately not stored, so a `due-soon` alert still correctly flips to `overdue` on its own between job runs even though the job itself doesn't repeat. `alerts:dismiss`/`alert_dismissals` unchanged. Known trade-off of "startup only": a cheque/bill that newly enters the 7-day window mid-session won't show up until the next app restart — accepted per explicit choice, not an oversight.
