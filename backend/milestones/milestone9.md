## Live backup database — follow-up (new scope, not in the original milestone list)
- **What was asked:** a second, live SQL Server database mirroring the main one, kept in sync automatically but never blocking main writes if it's briefly out of sync, plus a manual "Backup Now" button; the install-time NSIS wizard fixes the main install path (unchangeable) but adds one page asking where this backup database's files should live.
- [x] **Sync mechanism — native `BACKUP DATABASE`/`RESTORE DATABASE`, not row-by-row dual writes.** Replaying the same insert independently against two databases risks `IDENTITY` columns drifting apart (e.g. a sale bill header id vs. its item rows) — silently corrupting the "mirror" over time. `BACKUP DATABASE [main] TO DISK` then `RESTORE DATABASE [backup] FROM DISK WITH REPLACE` instead copies the exact committed state, ids included, every time, so it can never drift. `backend/src/services/backup.service.js`.
- [x] `ensureBackupDatabase()` — lazily creates the backup DB (`CREATE DATABASE ... ON (FILENAME=...)`) the first time a sync runs, using the folder from `appConfig.getBackupDbFolder()`, not at every startup.
- [x] `sync()`/`syncIfDirty()` — a module-level in-flight promise means a manual "Backup Now" click during an auto-sync just awaits the same run rather than racing a second `RESTORE`. `pool.js#withTransaction()` sets a `dirtySinceLastBackup` flag on every commit (every real write in this codebase goes through `withTransaction`, per the existing "Posting" convention); the 10-minute timer in `electron/main.js` calls `syncIfDirty()`, which no-ops (skips the BACKUP/RESTORE entirely) when nothing was written since the last sync. Failures are caught and logged, never surfaced to/blocking a main-DB write.
- [x] `backup:runNow`/`backup:status` IPC channels (admin-only, `requireRole('ADMIN')`) — `src/ipc/backup.ipc.js`; `frontend/src/pages/SettingsPage.tsx` gained a "Backup Database" card (admin credentials tab) with a Backup Now button and last-sync-time display.
- [x] **Install-time config:** `build/installer.nsh` — one custom NSIS page (via the `customPageAfterChangeDir` hook) asks for the backup folder, writes `%APPDATA%\Wentox\backup-config.json` (`{"backupDbFolder": "..."}`, backslashes converted to forward slashes since Node's `fs`/`path` accept either on Windows and it sidesteps JSON-escaping). `src/config/appConfig.js` reads/writes that file via Electron's `app.getPath('userData')` at runtime — `app.setName('Wentox')` added to `main.js` so that resolves to the same `%APPDATA%\Wentox` the installer wrote to (package.json's `name` is the npm-package `wentox-backend`, not this).
- **Debugger pass caught two real bugs, both fixed:** (1) `RESTORE DATABASE ... WITH REPLACE` with no `MOVE` clause would have restored using the *main* DB's own logical file names/paths (baked into the backup set), not the backup DB's — risking it overwrite the main DB's own files instead of landing in the backup folder. Fixed by reading the real logical names via `RESTORE FILELISTONLY` and building `MOVE` clauses dynamically. (2) ~~`customPageAfterChangeDir` is only inserted when `allowToChangeInstallationDirectory: true`, so the page would never appear; switched to `customPageBeforeInstall`.~~ **This finding was wrong and the "fix" broke the build twice** — verified against the actual template (`app-builder-lib/templates/nsis/assistedInstaller.nsh` lines 41-44): the `!ifmacrodef customPageAfterChangeDir` block sits *outside/after* the `!ifdef allowToChangeInstallationDirectory` block, so it is inserted unconditionally. There is no `customPageBeforeInstall` hook at all, so the renamed macro was never inserted, the `Page custom` lines were never emitted, and makensis failed with `warning 6010: install function ... not referenced` (electron-builder treats makensis warnings as fatal). Reverted to `customPageAfterChangeDir`. Lesson: check the installed template rather than trusting a claim about which hooks are conditional. Also hardened: `SET MULTI_USER` now runs in a `.catch()` so a failed RESTORE can't leave the backup DB stuck in `SINGLE_USER` forever; `sync()`'s dirty-flag consumption moved to the exact moment a NEW run starts (not when a caller joins an already-in-flight one), closing a narrow window where a write landing mid-sync could get marked "captured" without actually being in that backup; DDL identifiers now bracket-escaped.
- **Not yet live-verified** — no SQL Server reachable in this sandbox, and the NSIS installer itself needs a Windows build to test end-to-end (see 9.3's electron-builder note above).
- [x] **Follow-up: packaged installs can't ship `.env`.** `.env` is dev-only (and shouldn't carry a real shop PC's SQL Server password into git regardless), so `config/index.js` now checks `appConfig.getDbConnection()` first — populated by a second NSIS custom page (`build/installer.nsh`, before the backup-folder page) that asks for the SQL Server/port/database/username/password and writes them into the same `%APPDATA%\Wentox\app-config.json` the backup folder uses (file renamed from `backup-config.json` now that it holds more than that — safe since nothing has shipped yet). Falls back to `.env` only when that file doesn't exist, which is every dev checkout — confirmed with `DB_SERVER=localhost/DB_NAME=Wentox_db/...` env vars set and no app-config file present, `config.db` still resolves from `.env` exactly as before. Password field uses `ES_PASSWORD` (masked input); all values get JSON-escaped (backslash then quote) before being written.
- [x] **Follow-up: auto-migrate + auto-seed on launch.** A fresh shop-PC install has no schema/admin user yet, and running `npm run migrate`/`npm run seed` by hand isn't realistic for non-technical install. `migrate.js`/`seeds/run.js` now export their function instead of only self-invoking (`require.main === module` guard keeps `npm run migrate`/`npm run seed` CLI usage working unchanged); `electron/main.js`'s `app.whenReady()` now awaits both, before `registerIpcHandlers()`/`createWindow()`, on every launch — safe because both are already fully idempotent (`migrate` tracks `dbo.schema_migrations`; `seed`'s existence-checks per row already seed the default `admin`/`admin123` you asked for, unchanged). If SQL Server isn't reachable yet, this fails loudly to the console but still opens the window rather than hang the app. `migrate.js`'s `schema.sql` path now branches on `app.isPackaged` — dev keeps the monorepo-relative `../../../database/schema.sql`, packaged reads `resources/database/schema.sql`, since a packaged app never ships anything outside `backend/` unless explicitly added; `package.json`'s `extraResources` now also copies `database/schema.sql` in for that. **Not yet live-verified** for the same sandbox reason as above.
